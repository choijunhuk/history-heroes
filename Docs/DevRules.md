# 📏 개발 규칙

이 프로젝트를 만들 때 지키는 규칙이에요. 사람(개발자)과 AI(Claude Code, Codex) 모두 이 규칙을 따라요.

---

## 1. 게임 디자인 원칙 (흔들리면 안 되는 것)

1. **한 손, 세로 화면.** 모든 조작은 엄지 하나로 가능해야 한다.
2. **멈추면 쏜다.** 이동과 공격 사이의 긴장감이 핵심 조작이다.
3. **전설은 귀하다.** 초반에도 나올 수 있지만 끝까지 가도 잘 안 나온다. 확정 보장(천장)은 넣지 않는다.
4. **판 안의 선택이 판 밖 성장보다 중요하다.** 장비·룬이 아무리 좋아도 스킬 선택이 더 큰 차이를 만들어야 한다.
5. **기록은 노력의 결과다.** 잘 나온 판은 기록으로 남고, 그 기록으로 보스에 도전한다. 저장이 확률로 실패하는 일은 없다.
6. **인물을 존중한다.** 역사 인물을 비하하지 않는다. 코믹 스킨도 그 인물의 유명한 일화를 재밌게 비트는 정도로 한다.

## 2. 범위 규칙 (기능이 끝없이 늘어나는 것 방지)

- **로드맵 버전 순서대로 만든다.** 지금 버전이 끝나기 전에 다음 버전 기능을 시작하지 않는다.
- **새 아이디어는 [Ideas.md](Ideas.md)에 적는다.** 바로 만들지 않고, 지금 버전이 끝나면 검토해서 로드맵에 넣을지 정한다.
- **v0.1의 목표는 "재밌는지" 확인이다.** 그래픽은 네모와 동그라미로도 충분하다.

---

## 3. 폴더와 경로

- **경로에는 영어만 쓴다.** 한글이나 공백이 있으면 안드로이드 빌드(Gradle)가 실패할 수 있다.
- 유니티 프로젝트는 `Game/` 폴더에 둔다. 문서는 `Docs/`에 둔다.
- 스크립트는 기능별 폴더에 둔다. (`Scripts/Skills/`, `Scripts/Player/` 등. [기획서 11장](GameDesign.md#11-기술-메모) 참고)

## 4. C# 코딩 규칙

### 이름 짓기

| 대상 | 규칙 | 예시 |
|---|---|---|
| 클래스, 메서드, 프로퍼티 | PascalCase | `SkillManager`, `PickSkills()` |
| 인스펙터에 보이는 필드 | `[SerializeField] private` + camelCase | `[SerializeField] private float moveSpeed;` |
| 그 외 private 필드 | `_camelCase` | `_currentHp` |
| 지역 변수, 매개변수 | camelCase | `targetEnemy` |
| 상수 | PascalCase | `const int MaxSkillChoices = 3;` |
| 인터페이스 | `I` + PascalCase | `IRewardedAdService` |

### 작성 규칙
- **파일 하나에 클래스 하나.** 파일 이름 = 클래스 이름.
- **네임스페이스를 쓴다.** `HistoryHeroes.Skills`, `HistoryHeroes.Player`처럼 폴더와 맞춘다.
- **`public` 필드 대신 `[SerializeField] private`.** 다른 스크립트가 값을 마음대로 바꾸지 못하게 한다.
- **밸런스 숫자는 코드에 직접 쓰지 않는다.** ScriptableObject 에셋에 둔다. (예: 스킬 수치, 등급 확률)
- **`Update()` 안에서 `GetComponent`, `Find`를 부르지 않는다.** `Awake()`에서 미리 찾아둔다. (성능)
- **스킬 효과는 스킬마다 `Apply()`로 구현한다.** 거대한 `switch`문을 만들지 않는다.
- **주석은 한국어로, "왜" 이렇게 했는지 쓴다.** 코드만 봐도 알 수 있는 "무엇"은 쓰지 않는다.

## 5. 데이터와 저장 규칙

- **스킬 ID는 영어 소문자 + 밑줄로 짓는다.** (예: `multishot`, `fire_arrow`)
- **한 번 정한 ID는 바꾸지 않는다.** 이미 저장된 기록이 깨진다. 스킬을 없앨 때도 ID는 재사용하지 않는다.
- **저장 파일(JSON)에는 `version` 번호를 넣는다.** 구조가 바뀌면 번호를 올리고 예전 버전을 변환하는 코드를 둔다.
- **저장 위치는 `Application.persistentDataPath`.** 휴대폰마다 올바른 경로를 유니티가 알아서 정한다.

## 6. Git 규칙

### 기본
- **`main` 브랜치는 항상 실행 가능한 상태로 둔다.**
- 기능 하나는 브랜치 하나에서 만든다: `feature/스킬-선택-UI` 대신 **영어로** `feature/skill-select-ui`
- 버그 수정: `fix/arrow-not-hitting`

### ⚠️ 유니티에서 꼭 지킬 것
- **`.meta` 파일을 항상 같이 커밋한다.** 빠지면 다른 컴퓨터에서 연결이 다 끊긴다.
- **`Library/`, `Temp/`, `Logs/`, `UserSettings/`는 커밋하지 않는다.** (`.gitignore`가 막아준다)
- **비밀 정보는 절대 커밋하지 않는다.** 이 저장소는 **공개**다.
  - 안드로이드 서명 키(`.keystore`, `.jks`)와 비밀번호
  - 광고 SDK의 비공개 키, 결제 관련 비밀값

### 커밋 메시지
형식: `종류: 무엇을 했는지 (한국어 OK)`

| 종류 | 언제 | 예시 |
|---|---|---|
| `feat` | 새 기능 | `feat: 스킬 선택 카드 UI 추가` |
| `fix` | 버그 수정 | `fix: 관통 화살이 벽에서 사라지는 문제` |
| `balance` | 수치 조정 | `balance: 전설 확률 1층 1% → 0.8%` |
| `docs` | 문서 | `docs: 기록 시스템 기획 보완` |
| `refactor` | 동작은 같고 코드 정리 | `refactor: 스탯 계산을 StatSheet로 분리` |
| `chore` | 설정, 패키지 | `chore: URP 패키지 업데이트` |

- **커밋 전에 에디터에서 한 번 실행해본다.** 컴파일 에러가 있는 채로 커밋하지 않는다.

## 7. AI와 함께 작업하는 규칙

- **핵심 로직은 개발자가 직접 짠다.** 연습이 목적이다. AI는 뼈대와 `TODO` 자리를 만들고 설명한다.
  - 예: `PickSkills()` 가중치 뽑기는 직접 구현
- **AI는 이 문서와 [기획서](GameDesign.md)를 먼저 읽고 작업한다.**
- **기획이 바뀌면 기획서도 같이 고친다.** 코드와 문서가 다른 말을 하지 않게 한다.
- **큰 기획 변경은 Codex에게 리뷰를 받는다.** 리뷰 결과는 [Reviews/](Reviews/) 폴더에 남긴다.
